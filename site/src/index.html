ZEKNOP Signed Email

Developer Preview

Developer Preview — the protocol and the API may change; nothing on this page is a security guarantee

The protocol, the vectors an implementation is measured against, and the public part of the HTTP contract a relay answers — the package an implementation outside the publisher's repository is written from.

What this is

ZEKNOP is a protocol for signing an email so that the recipient can decide whether the text in front of them is the text that was signed. A signature is made over hashes of the message content, so what the protocol has to pin down is exactly which bytes are hashed, and in which order — that is what the specification does, and the vectors are how two implementations find out that they read it the same way.

This package is the public part of that work: four normative documents, the test vectors and the differential cases with reference answers, the paths a client outside the relay may call, two example clients, and a sandbox deployment to try it against. The current documents are version 1.4; signers of the current build announce X-ZEKNOP-Version: 1.5, and the HTTP contract described here is version 1.8.

Everything in the package is a file you can read and run on your own machine: the vectors need no network, no account and no key, and the example clients need nothing installed beyond a current Node.js or Python.

What this is not

  • Not a product and not an offer. This is a preview of a protocol and of an API, published so that implementations can be written against them. There is nothing to buy here and nothing to sign up for.
  • Not a guarantee. Nothing on this page or in this package is a security guarantee, and nothing here is a measurement of security, performance or privacy.
  • Not final. “Developer Preview” is meant literally: the protocol and the API may change, and the changes are recorded in the two changelogs the package carries.
  • Not a certification. Agreement with the vectors is a statement about bytes. Nobody is granting a mark, a badge or a licence for a matching report, and nothing here certifies an implementation.
  • Not the server. The relay's own source is not part of this package. What is here is the contract it answers on the public paths, generated from that application's own schema.

What is in the package

The links below point at the files of the package as https://docs.zeknop.org/ serves them. The same files are the repository zeknop/developer-preview; in a copy of it, they sit under its root.

The specification

Four documents: what is hashed, what the signature is made over, what a delivered message looks like, and what changed when. When two of them disagree, the one that is normative for the subject wins — and the README says which that is, step by step, in the order the protocol goes.

  • spec/README.md — start here: the quick start for v1.4 in seven steps
  • spec/canonical-content.md — what is hashed
  • spec/signature-input.md — what is signed
  • spec/delivered-envelope.md — what is delivered, and how a verifier takes it off
  • spec/CHANGELOG.md — the normative changes, version by version

Licence: CC BY 4.0. Each copied document carries the digest of the file it came from; the README of that directory is new text and carries none.

The test vectors

261 hand-written vectors in seven files, each holding inputs and the answers the specification requires for them, with a generator beside five of them that rebuilds the JSON from rules typed out of the specification and reports any difference, a validator that recomputes 72 of the 73 hashes in the largest file and reports the one it cannot, and no script at all for the six timestamp vectors, which are decisions rather than derived values. Beside them, 5 341 seeded differential cases ask the same questions over generated inputs — trim characters and their neighbours, line endings and their mixtures, combining sequences, character references, markup edges, forwards and replies, declared encodings over valid and invalid bytes, boundaries written with a character the trim set does not hold, and bodies over the size limit — and carry the answers of a reference implementation.

  • vectors/README.md — what each file fixes, and how to run it
  • vectors/CONFORMANCE.md — what to compare per file, and one report format so that two results can be read side by side
  • vectors/differential/cases.json — the seeded cases with their reference answers

Licence: CC BY 4.0. Python 3.11 or newer, standard library only.

The public HTTP contract

The paths a client needs in order to check a signature it received or to sign a message through a relay, the paths a verification portal reaches without a credential, and the paths by which an identity is obtained in a deployment that onboards without an external identity provider. The machine-readable document is generated from the relay's own schema and filtered to those paths; the README carries what a schema cannot state — what an answer means, and what a caller may do with it. Administration, billing, tenant configuration, signing keys, revocation and erasure are not part of this preview.

  • api/README.md — the semantics, path by path, with the status codes as they are
  • api/openapi-public.json — the OpenAPI document for the public paths (contract 1.8)
  • api/API-CHANGELOG.md — what changed for a caller, and when

Licence: CC BY 4.0. No server is listed in the OpenAPI document: the base URL is the relay you were given.

The example clients

Two small clients, each with the same three entry points: verify takes an .eml file, recomputes the hashes and asks a relay for the verdict (or, offline, only recomputes and compares against the headers); sign has a relay sign a message for an identity whose key you hold; conformance runs every vector file and the differential cases and prints the report. They are examples and not libraries: the JavaScript one has no run-time dependencies, the Python one is standard library only, and neither carries a warranty.

  • examples/js/README.md — the JavaScript client (Node.js 20 or newer)
  • examples/python/README.md — the Python client (3.11 or newer)

Licence: Apache-2.0, with LICENSE and NOTICE in each directory.

Where to start

  1. Read the quick start in spec/README.md. It walks the seven steps in the order the protocol goes, and names the vectors beside the steps they hold.
  2. Run the vectors against your implementation, file by file, and then the differential cases. vectors/README.md says what each file holds and how to run it.
  3. Report the result in the format vectors/CONFORMANCE.md fixes, with the digests of the vector files you actually read.
  4. Read api/README.md before you call a relay: the answers that are statements about a message, and the ones that are statements about the relay, are not the same answers.
  5. Compare against an example client when a hash comes out differently — the JavaScript one or the Python one. Both of them run the vectors as well, which makes them the shortest way to see which step disagrees.
